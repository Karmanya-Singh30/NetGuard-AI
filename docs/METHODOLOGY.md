# NetGuard AI — Methodology and mathematical foundations

This document explains **what the code does and why**, in the order the training script runs.
Every design decision here is implemented in `src/`. Numbers (dataset sizes, scores) are **not**
written here. They are generated by `python -m src.train` into `reports/results/`, so this
document can never disagree with the actual results.

---

## 1. Problem formulation

| Item | Definition |
|---|---|
| Input | One network **flow** (a bidirectional conversation summarised by CICFlowMeter) described by numeric statistics: durations, packet and byte counts, packet-length statistics, inter-arrival times, TCP flag counts, rates, bulk/subflow/active/idle statistics |
| Primary task | Binary classification: **ATTACK (1)** vs **BENIGN (0)** |
| Positive class | **ATTACK**. All of TP, FP, FN, precision, recall and FPR are defined relative to it |
| Secondary task | Multiclass attack-family classification: BENIGN, DoS, DDoS, PortScan, BruteForce, WebAttack, Bot, Infiltration, Heartbleed |
| Output | Predicted class, and P(ATTACK) from the model's `predict_proba` |
| Scope | Offline analysis of supplied flow records. **No** live packet capture or monitoring |

**Why binary first?** It is the operational question an analyst asks first ("is this
malicious?"). It has enough examples of both classes to learn and evaluate reliably. The
family model is added second, because some families have only a handful of examples.

## 2. Dataset

**CIC-IDS2017**, MachineLearningCSV release, Canadian Institute for Cybersecurity, University of
New Brunswick: https://www.unb.ca/cic/datasets/ids-2017.html. Cite: Sharafaldin, Lashkari &
Ghorbani, *Toward Generating a New Intrusion Detection Dataset and Intrusion Traffic
Characterization*, ICISSP 2018.

- Eight CSV files, one per capture session (Monday–Friday, July 2017). Each attack type was
  executed on a specific day; Monday is benign only.
- `Label` is the target. The release contains no IPs, timestamps or flow IDs. It does contain
  `Destination Port`.
- **Known limitations:** synthetic lab testbed traffic from 2017; documented labelling and
  flow-construction errors (Engelen, Rimmer & Joosen, 2021; Lanvin et al., 2022); attack types
  confounded with capture days; some attack classes are tiny.

The measured profile (row counts, missing/infinite values, duplicates, constant columns, class
distribution per file) is written to `reports/results/dataset_profile.json` and shown on the
website's Dataset explorer page.

## 3. Cleaning (`src/data_loading.py`, `src/data_preprocessing.py`)

| Problem in the raw files | Treatment | Why |
|---|---|---|
| Header names with leading spaces (`' Flow Duration'`) | Strip and collapse whitespace | The same names are needed in training, the app and user uploads |
| `Fwd Header Length` appears twice | Drop the copy, but only after verifying it is identical | Redundant column; verified rather than assumed |
| Web-attack labels contain an en-dash that decodes differently by encoding | Normalise to `Web Attack - …` | Otherwise one class splits into several |
| `Infinity` / `NaN` in `Flow Bytes/s`, `Flow Packets/s` (division by a zero duration) | ±inf → NaN, then **median imputation inside the pipeline** | sklearn models cannot take inf; the median is robust to the heavy tails |
| Non-numeric junk in numeric columns (if any) | Coerced to NaN and **counted** in the profile | Nothing is silently changed |
| Exact duplicate rows (same features **and** label) | Collapsed to one row **before the split** | Otherwise the same flow can sit in both train and test, which inflates scores |
| Identical features with **different** labels | All such rows removed and counted | No model can separate them, and they indicate labelling noise |
| Constant columns (e.g. bulk-rate fields that are always 0) | Removed by `VarianceThreshold(0)` **inside the pipeline** | Learned from training data only |
| `Destination Port` | Excluded from model inputs (`config.EXCLUDED_FEATURES`) | In this testbed, attacks target fixed ports, so the port is a shortcut that would not transfer to other networks. It is still used to judge duplicates and kept in the demo file |

**Why keep duplicates out but not "difficult" rows?** Duplicates are removed because they create
leakage across the split, not because they are hard to classify. No row is removed to improve
scores.

## 4. Splitting and leakage control

1. Clean and de-duplicate (above).
2. **Stratified 80/20 split** on the *fine-grained label* (seed 42), so even tiny classes appear in
   both parts. A class with a single row is stratified with its family.
3. The **test set is locked**. It is not used for imputation statistics, feature selection,
   hyperparameter tuning, the imbalance strategy, the decision threshold or the choice of the
   final model. It is only used to report the final numbers.
4. All learned transformations live in one scikit-learn `Pipeline`:

```
ColumnSelector(features) → SimpleImputer(median) → VarianceThreshold(0)
    → [signed log1p → StandardScaler]   (logistic regression only)
    → classifier
```

   Calling `.fit()` on training data fits every step on training data only. In cross-validation
   each fold refits the whole pipeline, so even the imputation medians never see the validation
   fold.
5. **Tuning subsample.** Cross-validation runs on a stratified subsample of the *training* split
   (default 200k rows). Every class keeps at least 2,000 rows, or all of its rows if it has fewer.
   This is for speed only. Final models are refit on the full training split, except on
   machines with less than 12 GB RAM, where they are fitted on a 1,000,000-row stratified
   subsample of the training split that keeps every rare-class row. The rule applied is recorded
   in `model_metadata.json` (`fit_rows_policy`) and must be stated in the report.
6. **Held-out-day check.** A second, harder evaluation: train on Monday–Thursday and test on all
   Friday flows. Friday's attacks (Bot, PortScan, DDoS) never occur in training. This measures
   generalisation to *unseen* attack types, which a random split cannot.

**Trade-off.** A random split measures how well the model recognises attack types it has seen
(the usual benchmark). A time-based split is closer to deployment but turns the task into
detecting new attacks. Both are reported, and the difference between them is itself a key result.

## 5. Feature selection (`src/feature_engineering.py`)

The dataset already provides ~78 engineered flow statistics, and no fields absent from the source
are invented. Four candidate sets are compared by 3-fold cross-validated F1 on the training
subsample, using a quick Random Forest:

| Candidate | How it is built (training data only) |
|---|---|
| All eligible features | Every numeric column except the label, bookkeeping and excluded columns |
| Correlation-filtered | Greedy: drop a feature when \|Pearson r\| > 0.98 with one already kept |
| Top-30 mutual information | Rank by \(I(X_j;Y)\) and keep the best 30 |
| Top-30 RF importance | Rank by Random Forest impurity importance and keep the best 30 |

**Rule:** choose the *smallest* set whose CV F1 is within 0.002 of the best set. Fewer features
mean a simpler input form, faster inference and an easier viva explanation, at no measurable
cost. RFE was not used: on hundreds of thousands of rows it is slow, and it adds no
interpretability over the importance ranking.

Mutual information:
\[ I(X;Y)=\sum_{x,y} p(x,y)\log\frac{p(x,y)}{p(x)p(y)} \]
It is zero when the feature tells us nothing about the class, and it captures non-linear
relationships that correlation misses.

## 6. Models (`src/train.py`)

All models use `random_state=42` where applicable and are tuned by `RandomizedSearchCV` (3-fold
stratified CV, scoring = **F1 of the ATTACK class**; recall, precision and specificity are also
recorded).

| Model | How it works | Why here | Tuned hyperparameters | Strengths | Weaknesses |
|---|---|---|---|---|---|
| **Dummy (majority)** | Always predicts the most frequent class (BENIGN) | Sanity baseline: shows what accuracy means on imbalanced data | none | Exposes misleading accuracy | Detects nothing (recall 0) |
| **Logistic Regression** | Linear score → sigmoid probability | Interpretable linear baseline; tests whether classes are linearly separable after log-scaling | `C` (inverse regularisation) | Fast, calibrated-ish probabilities, coefficients explain decisions | Cannot model interactions/thresholds unless engineered; needs scaling |
| **Decision Tree** | Recursive if/else splits that reduce impurity | Rules are human-readable; flow attacks often differ by thresholds (e.g. very short flows) | `max_depth`, `min_samples_leaf`, `criterion`, `class_weight` | Interpretable; no scaling | High variance, overfits when deep |
| **Random Forest** | Many decorrelated trees on bootstrap samples, averaged | Strong, robust standard for tabular NIDS data | `max_depth`, `min_samples_leaf`, `max_features`, `class_weight` | Low variance, handles non-linearity, built-in importance | Large model files; slower prediction; less transparent |
| **HistGradientBoosting** | Trees added sequentially to correct previous errors, on binned features | State-of-the-art accuracy on large tabular data; fast on millions of rows | `learning_rate`, `max_leaf_nodes`, `l2_regularization`, `class_weight` (early stopping on) | Usually most accurate; handles NaN natively; quick | More hyperparameters; can overfit; harder to explain |

**Final-model choice.** The model with the highest mean CV F1 on the *training* subsample is
chosen. Models within 0.001 of each other are tie-broken by CV specificity (fewer false alarms),
then by prediction speed. Test scores are reported afterwards and never feed back into the
choice.

**Overfitting check.** The script records mean *training-fold* F1 next to *validation-fold* F1
(`overfit_gap_f1` in `model_comparison.csv`). A large gap signals memorisation.

## 7. Mathematical foundations

### 7.1 Logistic regression
\[ z=\beta_0+\sum_{i=1}^{n}\beta_i x_i,\qquad P(y=1\mid x)=\sigma(z)=\frac{1}{1+e^{-z}} \]
The sigmoid squashes any real score into (0, 1). The model predicts ATTACK when
\(P \ge t\) (here \(t=0.5\), which is the same as \(z \ge 0\)). The coefficients are learned by
minimising the **binary cross-entropy** (log loss) with L2 regularisation:
\[ L=-\frac{1}{N}\sum_{k}\big[w_{y_k}\big(y_k\log p_k+(1-y_k)\log(1-p_k)\big)\big]+\frac{1}{2C}\lVert\beta\rVert^2 \]
\(w_{y}\) are the class weights (`class_weight="balanced"`, below). Smaller `C` means stronger
regularisation and smaller coefficients. Inputs are first transformed with
\(\operatorname{sign}(x)\log(1+|x|)\), because byte and time features span many orders of
magnitude, and then standardised (§7.5) so the coefficients are comparable.

### 7.2 Decision trees
Entropy of a node \(S\) with class proportions \(p_i\): \(H(S)=-\sum_i p_i\log_2 p_i\)

Information gain of splitting \(S\) into children \(S_v\):
\(IG=H(S)-\sum_v \frac{|S_v|}{|S|}H(S_v)\)

Gini impurity: \(Gini(S)=1-\sum_i p_i^2\)

At every node the tree tries thresholds on every feature and keeps the split with the largest
impurity reduction. A pure node has impurity 0. A tree grown until every leaf is pure memorises
noise (overfitting), so `max_depth` and `min_samples_leaf` limit growth. The criterion (gini or
entropy) is itself a tuned option.

### 7.3 Random Forest
1. Draw a **bootstrap sample** (with replacement) of the training rows for each tree.
2. At each split, consider only a **random subset of features** (`max_features`).
3. Grow many such trees \(h_1,\dots,h_m\).

The textbook rule is a majority vote, \(\hat y=\operatorname{mode}\{h_1(x),\dots,h_m(x)\}\).
**scikit-learn actually averages the trees' class probabilities**:
\(P(\text{ATTACK}\mid x)=\frac1m\sum_j P_j(\text{ATTACK}\mid x)\). It predicts ATTACK if this is
≥ 0.5. Randomisation decorrelates the trees, so averaging reduces variance without much increase
in bias.

When the final forest is fitted on millions of rows, each tree uses a bootstrap sample of at most
400,000 rows (`max_samples`). This is standard RF subsampling. It keeps memory, model size and
fit time bounded on a laptop, and because the trees are still decorrelated, accuracy is barely
affected. During tuning the CV folds are smaller than this cap, so nothing changes there.

### 7.4 Gradient boosting
\[ F_m(x)=F_{m-1}(x)+\eta\,h_m(x) \]
Each new small tree \(h_m\) is fitted to the negative gradient of the log loss of the current
ensemble \(F_{m-1}\), which roughly means it learns to correct the current mistakes. The learning
rate \(\eta\) shrinks each step. Smaller \(\eta\) needs more trees but generalises better.
Overfitting is controlled by `max_leaf_nodes`, L2 regularisation and **early stopping** (training
stops when a 10 % internal validation split stops improving). The histogram variant bins each
feature into ≤ 255 bins, which makes it fast on millions of rows.

### 7.5 Standardisation
\[ z=\frac{x-\mu}{\sigma} \]
\(\mu\) and \(\sigma\) are learned **from the training data only**. The same numbers are then
applied to validation, test and website inputs. Computing them on all data would leak test
information. It matters for logistic regression (gradient-based, penalised coefficients) but
not for trees, which only compare a feature with thresholds.

### 7.6 Class imbalance
**Class weights** (`balanced`): \(w_c=\frac{N}{K\,N_c}\) for \(K\) classes. Mistakes on rare
classes cost more in the loss.

**SMOTE** (compared for the family model):
\[ x_{\text{new}}=x_i+\lambda(x_j-x_i),\quad \lambda\sim U(0,1) \]
where \(x_j\) is one of the \(k\) nearest same-class neighbours of a minority sample \(x_i\).
It creates synthetic points on the line segments between real minority points. **It must be
applied only to training data.** Applied before the split, synthetic points derived from test
rows would leak into training, and the test set would contain points interpolated from training
rows. The code runs SMOTE inside an `imblearn` pipeline, so it is re-fitted inside each CV
training fold. No resampled row ever reaches a validation fold or the test set.

The SMOTE step uses a **floor strategy**: every class with fewer than 20,000 training rows
is topped up to 20,000, and larger classes are untouched. The library default copies every class
up to the majority size, which on ~2 million benign flows would create tens of millions of
synthetic rows. The final family model is fitted on a stratified subsample of at most 500,000
training rows that keeps every rare-class row.

The strategy for the family model (none / class weights / in-fold SMOTE) is chosen by CV
macro-F1. For the binary task, class weighting is part of each model's search space.

### 7.7 Decision threshold
The default threshold is 0.5. Lowering it catches more attacks (higher recall) at the price of
more false alarms (higher FPR). `reports/figures/threshold_sweep.png` shows this trade-off on
the test set **as an analysis only**. The threshold was fixed before looking at it. In practice
an operator would pick it from the cost of a missed attack versus the cost of a false alarm,
using validation data.

## 8. Evaluation metrics (`src/evaluate.py`)

With ATTACK as positive:

| Symbol | Meaning |
|---|---|
| TP | attack flow flagged ATTACK |
| FN | attack flow passed as BENIGN — **missed attack** |
| FP | benign flow flagged ATTACK — **false alarm** |
| TN | benign flow passed as BENIGN |

\[ Accuracy=\frac{TP+TN}{TP+TN+FP+FN}\quad Precision=\frac{TP}{TP+FP}\quad Recall=\frac{TP}{TP+FN} \]
\[ F1=2\frac{Precision\cdot Recall}{Precision+Recall}\quad Specificity=\frac{TN}{TN+FP}\quad FPR=\frac{FP}{FP+TN}\quad FNR=\frac{FN}{FN+TP} \]

- **ROC-AUC:** area under the TPR-vs-FPR curve across all thresholds; equals the probability
  that a random attack scores higher than a random benign flow.
- **PR-AUC (average precision):** area under precision vs recall. It is more informative than
  ROC-AUC when the positive class is rare, because it ignores the large TN count.
- **Undefined metrics** (e.g. precision when nothing is predicted ATTACK) are reported as
  `n/a`, not as 0 or 1.
- **Multiclass:** per-class precision/recall/F1, **macro** average (every class counts equally,
  so it exposes poor rare-class performance) and **weighted** average (weighted by support).
- **Why not accuracy alone?** With ~80 % benign traffic, the Dummy model already gets ~80 %
  accuracy while detecting nothing.

## 9. Error analysis

`reports/results/error_analysis.json` contains:
- missed attacks per label and family (which attack types slip through),
- the false-alarm rate on benign traffic,
- the distribution of P(attack) for FNs and FPs (confident errors versus borderline ones),
- median values of the top features for TP / FN / FP / TN, which shows whether missed attacks
  "look benign" on the features the model relies on,
- the threshold sweep.

## 10. Explainability (`src/explainability.py`)

| Method | Data | What it answers | Caveat |
|---|---|---|---|
| Built-in importance (trees: mean impurity decrease; LR: coefficients) | Training | What the model used to split / weigh | Impurity importance is biased toward high-cardinality features |
| Permutation importance | **Test** | How much test F1 drops when a feature is shuffled | Correlated features share credit and can each look unimportant |
| SHAP (tree models) / coefficient × value (LR) | Individual flows | Which features pushed *this* flow toward ATTACK or BENIGN | Describes the model, not causation, and does not prove a prediction is right |

## 11. Reproducibility

- One command regenerates every number and figure: `python -m src.train`.
- Fixed seed 42 for splitting, subsampling, CV folds and models.
- Exact library versions in `requirements.txt`. The training run records the environment in
  `models/model_metadata.json`.
- The website only reads saved artifacts. It never trains and never contains hard-coded
  results.
- Tests (`pytest`) cover loading, cleaning, leakage guards, schema validation, save/reload,
  metric definitions and the website pages.
