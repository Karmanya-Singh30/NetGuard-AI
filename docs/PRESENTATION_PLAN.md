# NetGuard AI — presentation plan (14 slides, ~12 minutes)

Every figure named below is generated by `python -m src.train` into `reports/figures/`, and
real website screenshots are in `docs/screenshots/`. All numbers come from the real run
(`reports/results/results_summary.md`).

| # | Title | Content (keep to ≤ 4 lines) | Visual | Speaker notes | Transition |
|---|---|---|---|---|---|
| 1 | NetGuard AI | Full title, team, guide, course, date | Shield icon + project name | Introduce yourself and the one-line aim: classify network flows as benign or malicious | "Why does this matter?" |
| 2 | Problem & motivation | Attacks are frequent and varied; analysts face volume; signatures miss variants | One simple diagram: traffic → flows → classifier → analyst | Frame it as triage support, not a firewall | "So what exactly did we set out to do?" |
| 3 | Objectives & use case | 4 objectives: leak-free pipeline, compare models, analyse errors, usable explainable tool. Users: students, analysts | Objective icons | State the scope: offline flow records, not live capture | "We needed real data for this." |
| 4 | Dataset & target | CIC-IDS2017, 8 days, ~78 flow features; target = Label → ATTACK vs BENIGN; 9-class family; 2,830,743 flows, 80.3 % benign, Heartbleed only 11 | `eda_class_distribution.png` | Explain a flow; positive class = ATTACK; mention imbalance | "Before modelling we looked hard at the data." |
| 5 | EDA findings | inf values, duplicated column, 331,200 exact duplicates (11.7 %), 8 constant columns, attacks tied to days | `eda_data_quality.png` + `eda_binary_by_day.png` | Each finding leads to a cleaning decision on the next slide | "Here's how each problem was fixed." |
| 6 | Preprocessing | Order: tidy → inf→NaN → targets → de-duplicate → stratified split → pipeline (impute, drop constant, scale for LR) | Pipeline flow diagram (from README Mermaid) | Stress *why de-duplicate before splitting* and *fit on train only* | "With clean data, which features matter?" |
| 7 | Feature selection | 4 candidate sets compared by CV on training data; rule = smallest within 0.002 F1; chosen: top-30 RF-importance features (CV F1 0.9954 vs 0.9937 for all 76) | Table from `feature_selection.json` | Port excluded as a testbed shortcut; no test data used | "Then the models." |
| 8 | Methodology & algorithms | Dummy, LR, DT, RF, HistGB; RandomizedSearchCV 3-fold, F1 (ATTACK); choice by CV only | 5-row table: idea / strength / weakness | One sentence of intuition per model; the Dummy shows the accuracy trap | "How does it fit together as a system?" |
| 9 | System architecture | Training pipeline → saved artifacts → Streamlit app; inference separate from training | README architecture diagram | The website never trains and has no hard-coded numbers | "And the results…" |
| 10 | Model comparison | Dummy accuracy 82.98 % / recall 0; LR F1 0.846, FPR 6.2 %; DT, RF, HistGB F1 ≈ 0.997; final Random Forest: recall 99.77 %, precision 99.64 %, FPR 0.074 % | `model_comparison.png`, `pr_curves.png` | Point to the Dummy's accuracy vs recall; explain why the chosen model was chosen | "Where does it go wrong?" |
| 11 | Confusion matrix & errors | FN 199 of 85,029, FP 308 of 414,592; all 4 SQL-injection, 5/7 Infiltration and 15 % of Bot flows missed; held-out Friday recall **10.1 %** | `cm_final_normalised.png`, `detection_by_family.png`, `holdout_day_detection.png` | Missed attack = FN, false alarm = FP; the random split vs the unseen-day gap is the honest headline | "Let's see it working." |
